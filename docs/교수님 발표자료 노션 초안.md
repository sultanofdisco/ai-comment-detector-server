# AI 댓글 탐지 시스템 발표자료 초안

## 1. 프로젝트 개요

본 프로젝트는 **크롬 확장 프로그램 기반 AI 댓글 탐지 시스템**이다.  
사용자가 X와 같은 플랫폼에서 댓글을 볼 때, 플러그인이 댓글을 수집하고 서버에 분석을 요청하면, 서버가 해당 댓글이 **인간 작성인지 AI 작성인지 1차 분류**한 뒤, 필요 시 **어떤 LLM 계열인지 2차 분류**를 수행한다.

즉, 목표는 단순한 텍스트 분류가 아니라:

- 브라우저 환경에서 실시간 댓글 수집
- 댓글 단위 인간/AI 판별
- AI 의심 댓글에 대한 LLM 계열 추정
- 이후 계정 단위 분석으로 확장 가능한 구조

를 만드는 것이다.

---

## 2. Plugin 파이프라인

### 2-1. 전체 흐름

1. 사용자가 X 댓글 페이지에 접속한다.
2. 크롬 확장 프로그램의 **content script**가 페이지의 댓글 DOM을 읽는다.
3. 댓글 텍스트, 작성자 ID, URL, timestamp 등의 정보를 추출한다.
4. 추출한 데이터를 **service worker**로 전달한다.
5. service worker가 서버의 `/predict` API로 분석 요청을 보낸다.
6. 서버 응답을 받으면 content script가 댓글 옆에 배지를 붙인다.
7. 상세 결과는 side panel 및 storage를 통해 재사용할 수 있다.

### 2-2. Plugin 내부 역할 분리

- **content script**
  - 댓글 DOM 탐색
  - 댓글 텍스트/작성자/링크 추출
  - 댓글 옆 배지 표시
- **service worker**
  - 서버 API 요청 관리
  - 캐시 및 메시지 전달
  - content script와 side panel 사이 중계
- **side panel**
  - 댓글별 AI 의심 점수
  - 최종 라벨
  - 근거 및 상세 결과 표시
- **chrome.storage**
  - 캐시 저장
  - 이후 블랙리스트/히스토리 관리 확장 가능

---

## 3. Server 파이프라인

### 3-1. 전체 흐름

1. 플러그인이 댓글 JSON을 서버로 전송한다.
2. 서버가 댓글 텍스트를 전처리한다.
3. **1차 모델(stage1)** 이 댓글을 **human vs ai**로 분류한다.
4. 1차 결과에서 AI 가능성이 충분히 높을 때만 **2차 모델(stage2)** 로 넘긴다.
5. 2차 모델은 AI 댓글을 `gpt / claude / gemini / deepseek` 중 하나로 분류한다.
6. 서버는 최종 라벨, AI 점수, 상위 후보 등을 JSON으로 반환한다.

### 3-2. 현재 모델 구조

- **1차 모델**
  - KC-BERT 기반
  - transformed text 입력
  - 목적: 인간 댓글과 AI 댓글 구분
- **2차 모델**
  - Hybrid 구조
  - KC-BERT 텍스트 분기 + stats feature 분기(XGBoost)
  - 목적: AI 의심 댓글의 LLM 계열 분류

### 3-3. 현재 API 구조

- `GET /health`
  - 서버 및 모델 로드 상태 확인
- `POST /predict`
  - 댓글 1개 입력
  - 인간/AI 여부 및 필요 시 LLM 계열 예측 반환
- `GET /admin/model-usage`
  - 관리자용 LLM 사용 빈도 집계

## 4. 왜 오탐(False Positive)이 심하게 발생했는가

현재 가장 큰 문제는 **사람이 쓴 댓글을 AI 댓글로 잘못 판정하는 오탐**이다.  
분석 결과, 원인은 모델 하나의 문제가 아니라 **데이터셋 분포 + 실제 X 도메인과의 차이 + 1차 모델의 한계**가 겹친 결과로 보인다.

### 4-1. 데이터 불균형

기존 stage1 학습 데이터는 대략 다음과 같이 구성되어 있었다.

- `human`: 2241개
- `ai`: 8836개

즉, 인간보다 AI 댓글이 약 4배 많았다.  
이 경우 모델은 자연스럽게 AI 쪽 패턴을 더 강하게 학습하게 되고, 실제 서비스 환경에서 사람 댓글까지 AI로 끌어당기기 쉬워진다.

### 4-2. 실제 X 댓글과 학습 데이터의 도메인 차이

실제 X에서 보이는 AI 댓글은 체감상 **더 길고, 설명형이며, 과하게 정돈된 경우가 많다.**  
반면 기존 데이터셋에는 비교적 짧고 공손한 AI 댓글도 많이 포함되어 있었다.

길이 분석 결과:

- `ai` 평균 길이: 약 `57.6`
- `human` 평균 길이: 약 `49.9`
- `human` 중앙값: `36`
- `ai` 중앙값: `49`

겉보기에는 AI가 더 길지만, AI 내부를 보면 분포 차이가 컸다.

- `claude` 평균: `37.2`
- `deepseek` 평균: `52.1`
- `gpt` 평균: `63.7`
- `gemini` 평균: `75.3`

즉, 일부 AI 데이터는 실제 X에서 보는 “긴 AI 댓글”보다 훨씬 짧고 공손한 톤에 가까웠고, 그 결과 짧은 인간 댓글과 구분이 어려워졌다.

### 4-3. 인간 댓글 중 오탐되기 쉬운 표현이 AI 데이터에 많이 포함됨

기존 데이터에서 다음과 같은 표현들이 AI 쪽에 과도하게 많았다.

- `축하`
- `ㅋㅋ`
- `ㅠㅠ`
- 공손한 존댓말
- 짧은 공감/위로형 답글

이 때문에 실제 인간 댓글이

- “축하드립니다!!”
- “ㅠㅠ 너무 고생하셨어요”
- “그럴 수도 있을 것 같네요”

처럼 짧고 정돈된 반응일 경우, 모델이 AI로 잘못 볼 가능성이 커졌다.

### 4-4. 1차 모델이 텍스트만 보는 구조

현재 1차 모델은 transformed text 기반의 KC-BERT 분류기다.  
즉, 문장 길이, 반복 패턴, 구두점 분포, 이모지 패턴 같은 통계적 특징을 직접 반영하지 않는다.

따라서 짧고 공손한 인간 댓글이 AI 댓글과 비슷한 문체를 보일 경우, 텍스트 정보만으로는 경계가 흐려질 수 있다.

### 4-5. 실서비스 환경에서는 오탐이 더 눈에 띔

테스트셋 성능이 높게 나와도, 실제 X 환경에서는 사람이 쓴 댓글이 훨씬 많다.  
이 상황에서는 작은 오탐률도 사용자 입장에서는 매우 크게 체감된다.

즉:

- 오프라인 테스트 성능은 높아도
- 실제 댓글 흐름에서는 오탐이 더 두드러져 보인다.

## 5. 현재까지 적용한 개선 사항

### 5-1. human과 ai를 1:1에 가깝게 맞추기 (완료)

stage1 학습 코드를 수정하여 **train split에서 human과 ai 비율을 1:1에 가깝게 맞추도록 변경**했다.

또한 AI 데이터는 `gpt / claude / gemini / deepseek`를 균등하게 남겨, 특정 LLM 쪽 문체만 과도하게 반영되지 않도록 조정했다.

핵심 효과:

- 인간 댓글이 소수 클래스로 밀리는 현상 완화
- 특정 LLM 스타일 편향 완화
- stage1이 human/ai 경계를 더 공정하게 학습할 수 있게 개선

### 5-2. dedup 및 threshold 튜닝 적용

학습 코드에서 중복 텍스트 제거와 validation 기반 threshold 탐색을 추가했다.

핵심 효과:

- train/test leakage 감소
- 서비스 환경에 맞는 threshold 선택 가능
- 무조건 0.5 기준으로 판단하는 문제 완화

## 6. 앞으로의 해결 방안

### 6-1. 데이터셋을 새로 만들기 또는 X 도메인에 맞게 재구성하기

가장 중요한 해결책은 **실제 X 댓글 분포를 더 잘 반영하는 데이터셋으로 재구성하는 것**이다.

방향:

- 실제 X에서 자주 보이는 AI 댓글 스타일 반영
- 긴 설명형/칭찬형/과잉 친절형 AI 댓글 보강
- 지나치게 짧은 AI 샘플은 비중 조절
- 인간 댓글도 X 특유의 짧은 리액션/욕설/감탄/이모지 스타일 반영

즉, 단순히 데이터 양을 늘리는 것이 아니라 **배포 도메인과 비슷한 분포로 다시 설계하는 것**이 중요하다.

### 6-2. human false positive 댓글 수집

두 번째 핵심 해결책은 **사람이 쓴 댓글인데 현재 모델이 AI로 오탐한 댓글을 따로 수집하는 것**이다.

이 데이터는 hard negative로 활용할 수 있다.

예:

- 짧은 축하 댓글
- 공손한 공감 댓글
- `ㅋㅋ`, `ㅠㅠ`, 이모지 포함 댓글
- 짧은 존댓말 리액션
- 반말/커뮤니티 톤 댓글

이 hard negative를 human 라벨로 추가하면, 모델이 “사람이 쓴 AI처럼 보이는 댓글”을 더 잘 구분할 수 있다.

권장 규모:

- 최소: `300~500개`
- 체감 개선: `1000개 이상`
- 오탐이 심한 현재 상황에서는 `1500~2000개` 이상이 가장 효과적일 가능성이 높다.

### 6-3. 필요시 1차 모델에도 stats feature 추가

현재 stats는 주로 2차 hybrid 모델에서 사용한다.  
하지만 오탐이 계속 심하다면, 1차 human/ai 구분 단계에도 stats feature를 넣는 방안을 고려할 수 있다.

추가 가능한 feature 예시:

- 문장 길이
- 공백 수
- 줄바꿈 수
- 반복 표현 비율
- 구두점 총개수 / 종류 수
- 특정 어미 패턴
- 웃음/감탄/이모지 반복 패턴

기대 효과:

- 텍스트 의미뿐 아니라 문체 패턴도 함께 반영
- 짧고 공손한 인간 댓글과 AI 댓글의 경계 보완

주의점:

- 서버 구조가 조금 더 복잡해짐
- 1차 추론 속도와 유지보수 비용이 증가할 수 있음

따라서 이 방법은 **데이터 재구성과 hard negative 추가 후에도 오탐이 심할 때 적용하는 2차 대안**으로 보는 것이 적절하다.

### 6-4. 실제 X 댓글 기반 평가셋 별도 구축

모델 개선 과정에서는 별도의 **실전 평가셋**이 필요하다.

추천 방식:

- 실제 X 댓글만 따로 수집
- human / ai 의심 댓글을 직접 검토
- stage1 성능을 서비스 도메인 기준으로 다시 측정

이렇게 해야 오프라인 테스트 성능과 실제 사용자 체감 성능의 차이를 줄일 수 있다.

## 7. 발표용 정리 문장

### 프로젝트 한 줄 요약

본 프로젝트는 크롬 확장 프로그램과 서버 기반 AI 분류 모델을 연결하여, X 댓글을 실시간으로 분석하고 인간/AI 여부와 AI 계열을 단계적으로 탐지하는 시스템이다.

### 현재 문제 한 줄 요약

현재 오탐이 심한 이유는 모델 자체의 단일 문제가 아니라, **데이터 불균형, 실제 X 도메인과의 분포 차이, 그리고 짧고 공손한 인간 댓글이 AI 데이터와 비슷하게 학습된 문제**가 겹쳤기 때문이다.

### 해결 전략 한 줄 요약

해결의 핵심은 **1차 stage1 데이터셋을 X 도메인에 맞게 재구성하고, human false positive를 hard negative로 추가하며, 필요시 stats feature까지 확장하는 것**이다.

---

## 8. 발표 슬라이드용 핵심 포인트

- 크롬 확장 프로그램이 댓글을 수집하고 서버에 전송
- 서버는 1차로 human/ai, 2차로 LLM 계열 분류 수행
- 현재 가장 큰 문제는 human 댓글의 오탐
- 원인은 데이터 불균형 + X 도메인 미스매치 + 1차 text-only 분류 한계
- human/ai 1:1 재조정은 이미 완료
- 다음 단계는 hard negative 수집과 X 스타일 데이터셋 재구성
- 필요시 1차 모델에도 stats feature 도입 검토
