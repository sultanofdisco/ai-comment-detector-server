# 프론트 연동 체크리스트

## 1. 문서 목적

이 문서는 크롬 확장 프로그램 프론트엔드 팀이 서버 API를 안정적으로 연동하기 위해 확인해야 할 항목을 정리한 체크리스트입니다.

현재 서버 파이프라인은 다음 순서로 동작합니다.

1. 프론트가 댓글 정보를 추출한다.
2. 서버가 1차로 `human` 또는 `ai`를 판별한다.
3. 1차 `ai_score`가 `0.85` 이상이면 서버가 2차로 LLM 계열(`gpt`, `claude`, `gemini`, `deepseek`)을 분류한다.
4. 프론트는 최종 결과를 댓글 옆 배지 또는 사이드 패널에 표시한다.

---

## 2. 연동 전 공통 확인 사항

- 서버가 실행 중인지 확인한다.
- `GET /health` 호출이 성공하는지 확인한다.
- 프론트에서 서버 베이스 URL을 환경별로 분리한다.
  - 예: 개발 `http://127.0.0.1:8000`
  - 예: 배포 `https://your-server-domain`
- `Content-Type: application/json` 으로 요청한다.
- 서버 응답이 실패할 경우 UI가 깨지지 않도록 기본 fallback 표시를 준비한다.

---

## 3. 프론트가 서버에 보내야 하는 입력 형식

프론트는 댓글 1개마다 아래 형식으로 `/predict`에 요청합니다.

```json
{
  "comment_id": "c1",
  "author_id": "user123",
  "text": "댓글 내용",
  "url": "https://x.com/...",
  "timestamp": "2026-03-30T12:00:00Z"
}
```

### 필드별 체크

- `comment_id`
  - 페이지 내에서 댓글을 다시 찾을 수 있는 고유값이어야 한다.
  - DOM 재렌더링 후에도 가능한 한 동일하게 유지되는 값이 좋다.
- `author_id`
  - 계정 단위 분석 확장을 위해 넣는다.
  - 없으면 빈 문자열로 보내도 되지만, 가능하면 항상 채운다.
- `text`
  - 실제 댓글 원문을 보낸다.
  - 프론트에서 임의 전처리하지 않는다.
  - 공백 제거, 줄바꿈 삭제, 특수문자 치환을 프론트에서 하지 않는다.
- `url`
  - 현재 댓글이 속한 게시물 URL을 넣는다.
  - 추후 로깅, 분석, 재현에 사용될 수 있다.
- `timestamp`
  - ISO 8601 문자열 사용
  - 예: `2026-03-30T12:00:00Z`
  - 없으면 프론트 수집 시각으로 대체 가능

## 4. `/health` 체크리스트

### 호출 목적

- 서버가 살아 있는지 확인
- 1차 모델과 2차 모델이 로드되었는지 확인
- threshold 값 확인

### 예시 요청

```http
GET /health
```

### 프론트 확인 포인트

- 응답이 `200` 인지 확인한다.
- 서버 시작 직후 확장 프로그램이 첫 분석 전에 `/health`를 한 번 확인하는 것이 좋다.
- 응답 실패 시 사용자에게 "분석 서버 연결 실패" 정도의 간단한 문구를 노출한다.

---

## 5. `/predict` 체크리스트

### 호출 시점

- 댓글 DOM이 화면에 나타난 뒤 호출한다.
- 무한 스크롤 환경에서는 새 댓글이 추가될 때마다 호출한다.
- 같은 댓글에 중복 요청하지 않도록 `comment_id` 기준 캐시를 둔다.

### 예시 요청

```http
POST /predict
Content-Type: application/json
```

```json
{
  "comment_id": "c1",
  "author_id": "user123",
  "text": "댓글 내용",
  "url": "https://x.com/example/status/1",
  "timestamp": "2026-03-30T12:00:00Z"
}
```

### 예시 응답

```json
{
  "comment_id": "c1",
  "pred_label": "gpt",
  "confidence": 0.91,
  "ai_score": 0.95,
  "top2": [
    ["gpt", 0.91],
    ["gemini", 0.06]
  ],
  "risk_level": "high",
  "reason": "stage1 ai_score >= 0.85, stage2 llm classification applied"
}
```

### 응답 필드 해석 규칙

- `comment_id`
  - 요청과 동일한 댓글 식별자
- `pred_label`
  - 최종 라벨
  - 가능한 값: `human`, `ai`, `gpt`, `claude`, `gemini`, `deepseek`
- `confidence`
  - 최종 라벨에 대한 confidence
  - `pred_label`이 `human` 또는 `ai`이면 1차 모델 confidence
  - `pred_label`이 LLM 라벨이면 2차 모델 confidence
- `ai_score`
  - 항상 1차 모델 기준 AI 확률
  - 프론트에서 "AI 의심 강도"로 사용할 때 가장 먼저 참고할 값
- `top2`
  - 2차까지 간 경우: LLM top2
  - 2차로 가지 않은 경우: 1차 `human/ai` top2
- `risk_level`
  - 서버가 계산한 위험 구간
  - 가능한 값: `low`, `medium`, `high`
- `reason`
  - 간단한 판별 근거 설명

---

## 6. 결과 표시 체크리스트

### 기본 표시 규칙

- `pred_label = human`
  - 별도 경고 없이 저위험 표시 또는 미표시
- `pred_label = ai`
  - "AI 의심" 배지 표시
  - 아직 특정 LLM까지는 분류되지 않은 상태
- `pred_label = gpt | claude | gemini | deepseek`
  - "AI 의심 / GPT 추정"처럼 표시 가능
  - 상세 정보는 side panel에 함께 보여주는 것을 권장

### `risk_level` 권장 해석

- `low`
  - 경고 강조를 최소화
- `medium`
  - 눈에 띄는 배지 표시
- `high`
  - 강한 강조 색상 또는 side panel 상세 유도

### `top2` 활용 방법

- tooltip 또는 side panel에 상위 2개 후보를 보여줄 수 있다.
- 메인 화면에는 `pred_label`만 간단히 노출하는 것이 좋다.
- 퍼센트 표시는 소수점 1자리 또는 2자리로 제한한다.

---

## 7. 프론트 구현 체크리스트

- 댓글 DOM에서 `comment_id`, `author_id`, `text`, `url`, `timestamp`를 추출한다.
- 댓글이 화면에 새로 나타날 때만 `/predict`를 호출한다.
- 같은 `comment_id`에는 중복 요청하지 않는다.
- 응답 결과를 `comment_id` 기준으로 다시 원래 DOM 요소에 매핑한다.
- 요청 중 상태를 표시할지 결정한다.
  - 예: 작은 로딩 점
  - 예: 분석 중 텍스트
- 분석 완료 후 배지 또는 라벨을 댓글 옆에 삽입한다.
- 상세 설명이 필요하면 side panel과 연결한다.

---

## 8. 에러 처리 체크리스트

### 서버 응답 실패 시

- 댓글 화면을 막지 않는다.
- "분석 실패"를 과하게 노출하기보다 조용히 skip 하거나 약한 안내만 표시한다.

### 권장 처리 방식

- `400`
  - 프론트 입력 형식 문제 가능성
  - 요청 payload를 콘솔에 기록하고 필드 누락 여부를 확인한다.
- `503`
  - 모델이 아직 로드되지 않았거나 서버 준비 중
  - 잠시 후 재시도 버튼 또는 자동 재시도
- `500`
  - 서버 내부 오류
  - 사용자에게는 일반 오류 메시지만 보여주고, 개발 중에는 콘솔 로그를 확인한다.
- 네트워크 오류
  - 서버 URL, CORS, 로컬 서버 실행 여부를 확인한다.

## 9. 테스트 체크리스트

### 최소 기능 테스트

- `/health`가 `200`으로 응답한다.
- 댓글 1개를 `/predict`로 보내면 JSON 응답이 정상 수신된다.
- `pred_label`에 따라 댓글 옆 배지가 다르게 표시된다.
- 무한 스크롤에서 새 댓글이 로드될 때 추가 분석이 동작한다.
- 동일 댓글에 중복 요청이 발생하지 않는다.

### 예외 상황 테스트

- 댓글 텍스트가 빈 문자열일 때 처리
- `author_id`가 없을 때 처리
- 서버가 꺼져 있을 때 UI fallback 처리
- 응답이 느릴 때 로딩 상태 처리

## 10. fetch 예시

```javascript
async function predictComment(comment) {
  const response = await fetch("http://127.0.0.1:8000/predict", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      comment_id: comment.comment_id,
      author_id: comment.author_id,
      text: comment.text,
      url: comment.url,
      timestamp: comment.timestamp,
    }),
  });

  if (!response.ok) {
    throw new Error(`Predict request failed: ${response.status}`);
  }

  return response.json();
}
```

## 11. 플러그인 팀이 특히 주의할 점

- 프론트에서 댓글 텍스트를 임의 변형하지 않는다.
- `ai_score`와 `confidence`는 의미가 다르다.
  - `ai_score`: 1차 인간/AI 판별 기준
  - `confidence`: 최종 라벨 confidence
- `pred_label = ai`는 "AI 가능성이 높지만 2차 LLM 분류 threshold 미만" 상태일 수 있다.
- 관리자용 LLM 사용 빈도 표는 2차 분류가 실제 수행된 결과만 집계한다.
- 현재 API는 댓글 1개 단위 호출이 기본이다.

## 12. 권장 연동 순서

1. `/health` 연동
2. 고정 샘플 댓글 1개로 `/predict` 테스트
3. 실제 DOM에서 댓글 추출 연결
4. 댓글 옆 배지 렌더링 연결
5. 중복 요청 방지 캐시 추가
6. side panel 상세 표시 연결
7. 에러 처리와 fallback 정리
